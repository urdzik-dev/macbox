# Архітектурні рішення (ADR) — MacBox

Цей документ фіксує дослідження, порівняння варіантів, гіпотези та (після Фази 2) реальні вимірювання для ключових архітектурних рішень.

---

## ADR-1: Захоплення екрана гостьової macOS

### Варіанти
- **(А) Гостьовий агент із `ScreenCaptureKit` (`SCStream`) всередині гостя**
  - *Дозволи:* Screen Recording видається **лише всередині гостя** для `MacBoxAgent.app`. Хост не потребує жодних TCC-дозволів.
  - *Ізоляція:* Хостовий процес ніколи не отримує доступу до екрана хоста.
  - *Масштабування та FPS:* `SCStreamConfiguration` дозволяє апаратно масштабувати кадр до точного розміру вікна терміналу (`width`/`height`) ще в гості й обмежувати `minimumFrameInterval`, а також отримувати кадри лише при зміні вмісту (`SCStreamFrameInfo.status == .complete`).
  - *Недолік:* Потребує одноразового надання дозволу Screen Recording всередині гостя (після Setup Assistant).
- **(Б) Захоплення `VZVirtualMachineView` на хості (через `ScreenCaptureKit` або `CGWindowListCreateImage`)**
  - *Дозволи:* Вимагає **Screen Recording на хості** (дає програмі доступ до всіх вікон користувача на хості — гірша ізоляція).
  - *Стабільність:* Залежить від наявності видимого/незгорнутого вікна `NSWindow` на хості; в headless-режимі або коли вікно перекрите/на іншому Space поведінка нестабільна.
- **(В) Публічний framebuffer API у `Virtualization.framework`**
  - *Перевірка SDK:* `VZGraphicsDisplay` **не надає** публічного доступу до пікселів. Недоступно без приватних API.
- **(Г) Вбудований macOS Screen Sharing (VNC / RFB) поверх мережі**
  - *Недолік:* Вимагає відкритого мережевого порту, ввімкнення Screen Sharing у гості, має вищу латентність і більшу поверхню атаки.

### Попередній вибір (до перевірки у Фазах 2–3)
**Варіант (А) — `ScreenCaptureKit` усередині гостьового агента.** Забезпечує нуль дозволів на хості, справжній headless-режим, апаратний даунскейл до розміру терміналу та event-driven захоплення без навантаження в простої.

## ADR-2: Ін'єкція вводу без впливу на хост

### Варіанти
- **(А) Синтез подій усередині гостя (`CGEvent` / `CGEventPost`)**
  - *Ізоляція хоста:* Події створюються та доставляються всередині гостьового віконного сервера (`WindowServer`). Курсор, фокус вікон і буфер обміну хоста **взагалі не зачіпаються**.
  - *Headless:* Працює навіть без відкритого вікна `VZVirtualMachineView` на хості.
  - *Дозволи:* Потребує Accessibility-дозволу лише для `MacBoxAgent.app` усередині гостя.
  - *Обмеження:* Події не працюють до першого входу в сесію (наприклад, на екрані LoginWindow / Setup Assistant) — для Setup Assistant використовується нативне вікно `VZVirtualMachineView` на етапі ініціалізації.
- **(Б) Доставка `NSEvent` у `VZVirtualMachineView` на хості**
  - *Перевірка SDK:* `VZVirtualMachineView` приймає системні події AppKit, коли вікно активне й у фокусі. Програмна відправка синтетичних `NSEvent` у приховане/нефокусне `VZVirtualMachineView` ненадійна, а реальний клік/фокус заважає користувачу на хості.

### Попередній вибір
**Варіант (А) — синтез `CGEvent` усередині гостя** для звичайної роботи та MCP; нативне `VZVirtualMachineView` використовується лише під час первинного Setup Assistant або за явною командою `macbox view --window`.

## ADR-3: Транспорт хост ↔ гість (підлягає прототипуванню та вимірам у Фазі 2)

> **Принцип:** Не обираємо транспорт наосліп. У Фазі 2 прототипуємо робочі кандидати на реальній macOS-VM і заповнюємо таблицю нижче.

### Кандидати

| Кандидат | API на хості | API у macOS-гості | Мережевий слухач? | Гіпотеза щодо латентності / пропускної здатності | Поверхня атаки / Ризики |
|---|---|---|---|---|---|
| **1. `vsock` (`VZVirtioSocketDevice`)** | `VZVirtioSocketDevice` (`connect(toPort:)` / `VZVirtioSocketListener`) | `socket(AF_VSOCK, SOCK_STREAM, 0)` із `<sys/vsock.h>` (`VMADDR_CID_HOST = 2`) | **Ні** | Дуже низька латентність (< 1 ms), потокова передача кадрів без дискового I/O | Потрібно перевірити наживо: чи працює `AF_VSOCK` у unprivileged macOS-гості та чи немає backpressure-зависань при великих кадрах |
| **2. `virtio-fs` mailbox (`VZVirtioFileSystemDevice`)** | Звичайна папка на хості (`VZSingleDirectoryShare`) | `/Volumes/My Shared Files` (`macOSGuestAutomountTag`) | **Ні** | Середня латентність (5–30 ms через FS polling/FSEvents), надійний обмін файлами | Потребує суворої перевірки symlink/hardlink (`O_NOFOLLOW`), лімітів розміру, очищення завислих файлів, атомарних `rename` |
| **3. TCP через NAT (`VZNATNetworkDeviceAttachment`)** | Локальний TCP-клієнт/сервер на вузькому інтерфейсі (`bridge100`) з токеном | Стандартний BSD TCP socket | **Так** (порушує принцип «без слухача за замовчуванням») | Низька латентність (~1–2 ms), висока пропускна здатність | Потребує визначення IP гостя (DHCP lease), відкриває TCP-порт, потребує автентифікації токеном і захисту від інших клієнтів у NAT-підмережі |
| **4. Virtio Console / Serial (`VZVirtioConsoleDevice`)** | `VZVirtioConsolePort` (`Pipe` / `FileHandle`) | `/dev/cu.virtio*` або `/dev/tty.*` (потрібно перевірити, чи створює macOS-гість вузол) | **Ні** | Невідомо (може бути низька пропускна здатність або відсутній драйвер у macOS-гості) | Потребує фреймінгу поверх байтового потоку; висока ймовірність відсутності драйвера в macOS-гості |

## ADR-4: Формат кадрів і стрімінг у термінал

### Питання для перевірки у Фазах 2 і 4
1. **Повні кадри vs дельти (dirty rects):**
   - `SCStream` надає `SCStreamFrameInfo.dirtyRects`. Для термінальних протоколів (Kitty / iTerm2) повний кадр, уже відмасштабований до піксельного розміру вікна терміналу (наприклад, 1280×800 або 960×600), часто менший і простіший за композитинг дельт, а Kitty підтримує заміну зображення по `i=<id>`. Проте при локальних змінах (миготіння курсора) часткове оновлення або хеш-перевірка (skip identical frames) економить CPU.
2. **Стиснення:**
   - Порівняємо у Фазі 2: `COMPRESSION_LZ4` (Apple `Compression` framework — надшвидке, мінімум CPU), `COMPRESSION_ZLIB` (підтримується нативно Kitty `o=z`), та PNG (потрібен для iTerm2 OSC 1337 і MCP `screenshot`).
3. **Доставка в термінал:**
   - **Kitty / Ghostty:** передача через POSIX Shared Memory (`shm_open`, `t=s`) — уникає base64-кодування мегабайтів через PTY.
   - **iTerm2 / fallback:** OSC 1337 (`File=inline=1;...`) із PNG-кодуванням.
4. **Адаптивний FPS:**
   - 0 fps при незмінному екрані; до 30 fps під час активної взаємодії; автоматична пауза стріму через N секунд після відключення viewer.

## ADR-5: Налаштування гостя (Setup Assistant і TCC)

### Перевірені обмеження macOS
1. **Setup Assistant:** У публічному `Virtualization.framework` (перевірено по `MacOSX26.sdk`) **немає** API для автоматичного проходження Setup Assistant. Отже:
   - **Фази 1–6:** Кероване налаштування — `macbox up` відкриває вікно `VZVirtualMachineView`, користувач один раз проходить Setup Assistant і встановлює/дозволяє `MacBoxAgent.app`.
   - **Подальше використання:** Після одноразового налаштування «золотого» образу всі нові середовища створюються миттєво через `macbox clone` (APFS `clonefile`), тому Setup Assistant і TCC не доводиться проходити повторно.
2. **TCC (Screen Recording та Accessibility у гості):**
   - macOS навмисно блокує програмне редагування `TCC.db` без згоди користувача або MDM-профілю (PPPC).
   - Щоб дозволи зберігалися між оновленнями `MacBoxAgent.app`, бандл агента має підписуватися стабільним локальним сертифікатом (або стабільним designated requirement), інакше macOS інвалідує TCC-запис.
   - Ми чесно документуємо це обмеження в `README.md` і не використовуємо хаків на кшталт вимкнення SIP.
